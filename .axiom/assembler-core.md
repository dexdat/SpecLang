# SpecLang — Architectural Core (Assembler, Not Compiler)

## The Assembler Definition

SpecLang is a **multi-language source code assembler**. It does not compile code — it assembles it.

```
Human writes:   project.scl (one file — intent, vision, high-level goal)
                    │
                    ▼
SpecLang expands:   specs/ (hundreds of spec files — autonomously generated)
                    │  spec-writer agents go wide, ask questions,
                    │  build the full spec tree, cascade expanding into cascade
                    ▼
SpecLang assembles: src/ (code files in any language — PHP, Python, Go, Ruby,
                         Rust, C, Java, TS, ...)
                    │
                    ▼
Target compiler:    binary / executable / package
                    (gcc, rustc, tsc, go build, javac, ...)
```

SpecLang's job has **two phases**:

1. **Spec expansion** — The human writes ONE seed spec (e.g., `project.scl`). SpecLang's spec-writer agents autonomously question, expand, and build all subsidiary spec files needed to fulfill that intent. *This is where the intelligence lives.* The agents think: "What specs do we need? What are the entities? The operations? The data models?" They create the full spec tree.

2. **Code assembly** — The codegen agents read the expanded spec tree and assemble source code files for each `{name}.{ext}.spec` target. The target language's compiler finishes the job.

## The Cascade Multiplies

A single human edit to one spec file does not just regenerate one output file. It cascades:

```
Human edits:  specs/core/entities.spec.md   (one line changed)
                    │
                    ▼
Cascade 1:    FileChangeEvent → cascade router
              Finds every @ref:specs/core/entities in all 440+ specs
              Marks 30 dependent specs as "needs review"
                    │
                    ▼
Cascade 2:    Spec-writer agent evaluates each dependent spec
              "Does this spec need updating based on the entities change?"
              Creates/updates 15 spec files
                    │
                    ▼
Cascade 3:    Each changed .spec.md triggers codegen agents
              Assembles the corresponding .go / .ts / .py files
                    │
                    ▼
Cascade 4:    Pipeline: build → test → lint → commit
                    │
                    ▼
              Each generated source change triggers MORE cascades
              (because codegen output may reveal missing specs)
              → MULTIPLYING CASCADES, concurrent within pool limits
```

The multiplying cascade is NOT a bug — it's the core mechanism. SpecLang intentionally "goes wide," continuously asking itself what needs to exist and building it. The user's single high-level intent expands into a full system.

## File Extension Convention

| Pattern | What it is | Example |
|---------|-----------|---------|
| `project.scl` | **Seed spec** — human writes ONE of these. The root intent. | `project.scl` |
| `{name}.spec.md` | **Spec file** — source of truth. Generated by spec-writer agents (or edited by humans). | `auth.spec.md` |
| `{name}.{ext}.spec` | **Code assembly target** — describes what `{ext}` code to generate. | `auth.handler.go.spec` |

The folder structure of `specs/` mirrors the intended output structure. A spec at `specs/api/auth/login.spec.md` assembles code at `src/api/auth/login.go`.

The human never writes 100 spec files. The human writes ONE file (project.scl or equivalent). SpecLang's spec-writer agents expand it. The human can then surgically edit any generated spec file to tweak behavior — and that single edit triggers its own cascade.

## Header Controls Everything

```yaml
# speclang-header lines:15
id: "@specs/api/auth"
version: 1.0.0
layer: 3
project_level: Alpha
agent_support: agent_autonomous
model: openai/gpt-4o              # Which model assembles this file
model_pool: code-gen              # Or which capability pool
max_concurrent: 3                 # Rate limit for this model
tags: [api, auth, go]
short: Authentication API
depends_on:                       # Upstream dependencies
  - "@ref:specs/core/entities"
children:                         # Sub-specs (specs this one expanded into)
  - "@ref:specs/api/auth/login"
  - "@ref:specs/api/auth/register"
target_lang: go                   # Output language
output: src/api/auth/handler.go   # Output path
owned-by: codegen                 # Which agent role owns this
seed: false                       # true = human-written, false = agent-generated
```

## Self-Expanding Spec Tree

The human writes one file. SpecLang does the rest:

```
project.scl  (human writes this)
    │
    ▼  [spec-writer agent reads project.scl, thinks: "what specs are needed?"]
    │
    ├── specs/core/entities.spec.md              (agent-generated)
    ├── specs/core/operations.spec.md            (agent-generated)
    ├── specs/api/auth.spec.md                   (agent-generated)
    │   ├── specs/api/auth/login.spec.md         (agent-generated, from auth.spec.md cascade)
    │   ├── specs/api/auth/register.spec.md      (agent-generated, from auth.spec.md cascade)
    │   ├── specs/api/auth/login.handler.go.spec (agent-generated, from login.spec.md cascade)
    │   └── specs/api/auth/register.handler.go.spec
    ├── specs/api/users.spec.md                  (agent-generated)
    ├── specs/db/migrations.spec.md              (agent-generated)
    └── ...                                      (agents keep expanding until convergence)

    ▼  [codegen agents assemble source files from the spec tree]
    │
    ├── src/api/auth/login.go
    ├── src/api/auth/register.go
    ├── src/db/migrations/
    └── ...
```

Each agent generation step is itself a cascade. The spec-writer agent outputs new spec files, which trigger file-change events, which trigger the spec-writer agent AGAIN to expand those new specs. This continues until convergence (no new specs needed).

**The user can intervene at any point.** They open `specs/api/auth/login.spec.md`, make a tweak, save it. That single edit triggers a new cascade that propagates through the system — updating dependent specs and regenerating code. The user doesn't touch code files, just spec files.

## Squash and Throttle

Because cascades multiply, we need two controls:

### Squash

Multiple rapid changes to the same spec file are squashed into a single cascade. If the user saves `auth.spec.md` three times in two seconds, the cascade router debounces: it waits 100ms, collects all pending changes, and fires ONE cascade with all changes batched.

At the cascade level: if cascade N is still running when cascade N+1 triggers for overlapping specs, the second cascade waits and squashes its work into the first where possible.

### Throttle

Prevent runaway cascade multiplication:
- **Max cascade depth**: configurable (default 5). A cascade deeper than 5 levels triggers a throttle warning.
- **Max concurrent cascades**: per-pool and global limits. If 50 cascades are running, queue.
- **Rate limit**: max N cascades per minute globally.
- **Circuit breaker**: if cascades produce errors (pipeline failures, agent timeouts) at >50% rate, throttle to 1 cascade per 5 minutes and notify the user.

## Model Pools and Rate Limits

Users bring their own API keys from multiple providers:

```
Provider A (OpenAI)               Provider B (OpenRouter)
├── gpt-4o: 5 concurrent          ├── gpt-4o: 10 concurrent
├── gpt-4o-mini: 20 concurrent    ├── gpt-4o-mini: 50 concurrent
└── dall-e-3: 2 concurrent        └── claude-3-opus: 5 concurrent

SpecLang Pool Configuration:
  pool "code-gen":
    - openai/gpt-4o (5 concurrency)
    - openrouter/gpt-4o (10 concurrency)
    → Effective: 15 concurrent gpt-4o agents
    → Rate-limited by each provider's cap
    → Same model name = same pool group

  pool "spec-writer":
    - openai/gpt-4o (5 concurrency)
    - openrouter/claude-3-opus (5 concurrency)
    → Different models, same capability (spec writing)
    → Agent uses whichever is available

  pool "cheap":
    - openai/gpt-4o-mini (20 concurrency)
    - openrouter/gpt-4o-mini (50 concurrency)
    → 70 concurrent, for low-stakes specs
```

Rules:
- Same model from different providers → pooled together for bigger effective rate limit
- Different models with same capability → grouped in a named pool by purpose
- Providers may offer downgraded variants (e.g., GitHub's 128K context vs 400K) — user flags as `quality: downgrade`, system avoids for critical work
- Each pool has `max_concurrent` enforced by cascade router
- Models in a pool tried round-robin or by availability

## Dependency Graph — The Cascade Engine

When a spec file changes:

1. **Read header** — `depends_on` = upstream specs that affect this one. `children` = downstream specs this one feeds.
2. **Trace ref graph** — Every `@ref:` in every header creates an edge. The graph spans all `specs/`.
3. **Impact analysis** — Change `specs/core/entities.spec.md`? Find every spec that refs it and mark as needing re-assembly.
4. **Batch dispatch** — Group affected files by `model_pool`. Respect `max_concurrent` per pool. Dispatch Pi agent sessions.
5. **Cascade cascades** — Each spec-writer agent output triggers its OWN FileChangeEvent, causing another cascade round. This is NOT a bug — this is the expansion mechanism. Squash + throttle prevent runaway.

## What Controls Which Model Writes a File

Three-layer resolution (first match wins):

1. **Header `model:` field** — explicit model for this specific spec file
2. **Header `model_pool:` field** — named pool (all models with this capability)
3. **File pattern** — `specs/**/*.spec.md` maps to "spec-writer" pool, `**/*.go.spec` maps to "code-gen" pool

The header always wins. An individual spec can override the default model for its role.

## Assembler vs Target Compiler

| SpecLang (Assembler) | Target Language (Compiler) |
|---|---|
| Reads `.spec.md` files | Reads `.go`, `.rs`, `.ts`, `.py` files |
| Produces source code in any language | Produces binaries, bytecode, or executables |
| Uses LLM agents to generate code | Uses deterministic compilation rules |
| Self-expanding: agents create more specs | Fixed: reads what's there |
| Handles cross-file deps via `@ref:` | Handles import/module resolution |
| `owned-by` + `model` controls who writes | No concept of "who writes" |

## Bootstrap Path to Self-Hosting

Everything we build during bootstrap is in SpecLang format so SpecLang can take over:

```
Bootstrap phase (right now):
  1. Hermes writes specs/assembler/*.spec.md   ← source of truth
  2. Hermes hand-writes .speclang/*.ts          ← placeholder (hand-generated)
  3. Symlink: specs/assembler/*.spec.dir/src/*.ts → .speclang/*.ts

Bootstrap moment:
  4. SpecLang reads specs/assembler/daemon.spec.md
  5. SpecLang generates .speclang/daemon.ts
  6. Verify: generated code matches hand-written

Self-hosting:
  7. Edit specs/assembler/daemon.spec.md
  8. SpecLang regenerates everything
  9. Delete hand-written .ts files
  10. SpecLang builds SpecLang forever
  11. Throw away Hermes, Axiom, OpenCode — all external tools
```

No `.ts` file without a `.spec.md` that describes it. Every file we produce during bootstrap is a hand-generated placeholder that SpecLang will regenerate from specs.
