## Architecture Summary (Read This First)

### Three File Types
1. `{name}.spec.md` — Informational spec. Describes concepts, architecture, design. No code pair. Lives in folder structure.
2. `{name}.spec.{lang}.md` — Code-pair spec. Design doc for a specific code file in language {lang}. Has a 1:1 pair with the generated code file.
3. `{name}.spec.{lang}` — Generated code. The actual implementation in language {lang}. Written by the model from the code-pair spec + all refs + folder context.

### The Header
Every {name}.spec.{lang}.md file has a YAML header that controls ALL assembly decisions:

```yaml
# speclang-header lines:20
id: "@specs/cron-system/job-runner"
version: 1.0.0
layer: 3
project_level: Alpha
agent_support: agent_autonomous
target_lang: go
output: internal/cron/job-runner.spec.go
owned-by: codegen
model: openai/gpt-4o
model_pool: code-gen
max_concurrent: 3
rate_limit: 5
quality: production
seed: false
tags: [cron, job-runner, go]
short: Cron job runner implementation
depends_on:
  - "@ref:specs/cron-system/cron-system.spec.md"
  - "@ref:specs/sdk/cron-driver/client"
watch:
  files:
    - "specs/cron-system/cron-system.spec.md"
    - "specs/sdk/cron-driver/*.spec.md"
  exclude:
    - "specs/sdk/cron-driver/legacy.spec.md"
children:
  - "@ref:specs/cron-system/job-runner/types"
status: active
```

### The Watch System
Header `watch:` fields define the notification graph alongside `@ref:` links in the spec body. When any file matching a watch pattern changes, all specs that watch it get notified. The cascade router merges both sources: `depends_on` refs + `watch.files` patterns + body `@ref:` links.

### Assembler vs Compiler
SpecLang is an ASSEMBLER, not a compiler:
- Assembler: reads `.spec.{lang}.md` files → produces `.spec.{lang}` source code in any language
- Compiler: target language's compiler (gcc, rustc, tsc, go build) compiles the `.spec.{lang}` files
- The assembler uses LLM models (from header model/pool fields) to generate code
- Codegen is a CORE SpecLang module, not a separate tool

### Model Pools
Users bring keys from multiple providers. Same model from different providers pools concurrency. Different models with same capability group in named pools. Headers control which model/pool writes each file.

### Throttle — Fairness Queue with Deferral
When the same file gets hammered by rapid cascades, it's deferred to the back of the queue. Other files process while it waits. On requeue, one more chance. Escalating backoff. User notified after 3 deferrals.

### Squash
Rapid changes to the same file within 100ms window are debounced into one cascade. Overlapping cascades merge.

### Cascade Depth / Multiplying
A single spec change can trigger multiple levels of cascades as agents generate new specs, which trigger more cascades. This is by design — it's how the spec tree expands. Controlled by squash + throttle.

### 5. specs/cascade.spec.md — UPDATE FOR NOTIFICATION GRAPH + THROTTLE + SQUASH

Add section for **Notification Graph**:
- Merge two sources: explicit `depends_on` refs + `watch.files` patterns from headers + `@ref:` links from spec body
- When any file matching a watch pattern changes, all specs that watch it get a change event
- The graph is a directed graph from dependency sources to dependent specs

Add section for **Squash**:
- Debounce: multiple rapid changes to same file within 100ms are merged
- Cascade merge: if cascade N is running and cascade N+1 triggers for overlapping files, merge work

Add section for **Throttle** (fairness queue with deferral):
- Track how many times each file has been queued in last 60s
- Files exceeding threshold (default 5) marked "hot" and deferred to back of queue
- Other files process while hot file waits
- On requeue: one more cascade attempt
- If still hot: escalating backoff (2x, 4x, 8x)
- After 3 deferrals: notify user
- No cascade is ever cancelled — only postponed

Add section for **Model Pool Dispatch**:
- Read header model/model_pool field from each changed spec
- Group affected specs by model_pool
- Respect max_concurrent per pool (from config + header)
- Dispatch Pi agent sessions accordingly
