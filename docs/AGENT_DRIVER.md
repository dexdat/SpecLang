# Agent Driver — running SpecLang from another coding agent

**Audience:** an agent session (Hermes, OpenCode, Claude Code, Codex CLI, or any
harness with a shell) that has been told to *use* SpecLang, not to develop it.
**Not** a human-typing-CLI guide — that is [`GETTING-STARTED.md`](../GETTING-STARTED.md).

This guide describes one loop, end to end:

```
driver writes ONE seed  →  speclang expands it into artifacts  →  driver verifies
                                   ↓
                     per-stage progress record on disk
```

The loop is designed to be run unattended and to **fail closed**: a step that
produced nothing must not be reported as success. Every command in
[§4 Runbook](#4-runbook-fresh-clone-verbatim) is verified to exit 0 on a clean
checkout; the negative probes in [§7](#7-what-the-driver-refuses-negative-probes)
are verified to exit non-zero *for the reason stated*.

---

## 1. The idea: one seed, speclang fills in the rest

SpecLang's unit of work is a **spec file**, and a spec file is a prompt. A block

````
### @block::greeting @kind:code
```ts
export function greet(name: string): string { return `Hello, ${name}!`; }
```
````

is a prompt whose answer is already written: the cascade copies the fenced body
into a file. The driver therefore writes **one** baseline seed and lets SpecLang
produce the file set from it, rather than hand-writing every output file.

There are two expansion paths in the shipped code. Know which one you are on.

| Path | What fills in the extra prompts | Credentials | Writes files? |
|---|---|---|---|
| **A. Deterministic cascade** (default, documented below) | the seed itself — every `@block` becomes a file | none | yes, `<seed-dir>/../generated/` |
| **B. LLM agent expansion** (opt-in, §8) | `speclang agent` sessions driven by the daemon; the model's `# generated/<path>` sections are persisted by `CascadeCoordinator.persistAgentOutput` | one provider API key | yes, into the paths the model marks |

Path A is what a driver should use unless the task genuinely needs a model to
invent content: it is deterministic, takes ~0.1 s, needs no network, and its
failures are detectable (see §7). Path B is real but experimental — it requires
an LLM provider and its output is model-shaped.

### Credentials, stated plainly

- **The cascade needs no API key at all.** `speclang cascade` is a template
  compiler: spec blocks in, files out.
- `DEEPSEEK_API_KEY` is **not** a SpecLang provider. The provider adapter accepts
  exactly `openai`, `openrouter`, `anthropic`, `google`/`gemini`
  (`src/cascade/provider-adapter.ts`). Anything else fails immediately:
  `Unsupported LLM provider "deepseek"` (exit 1, verified §7). In this repository
  `DEEPSEEK_API_KEY` is the GitReins tier-2 judge's key (`specs/ci.spec.md`), not
  something SpecLang reads.
- If a task requires an LLM stage, set `OPENAI_API_KEY`,
  `OPENROUTER_API_KEY`, `ANTHROPIC_API_KEY` or `GEMINI_API_KEY` and use §8.

## 2. Where the artifacts land

One rule, no exceptions:

```
<artifacts> = <directory containing the seed>/../generated/
```

- seed `scripts/agent-driver/seed.example.spec.md` → `scripts/generated/`
- seed `specs/foo.spec.md` → `generated/` (project root)
- seed `tests/agent-driver/seed.spec.md` → `tests/generated/`

Each `@block::<name>` becomes `<name with '-' → '_'>.ts`; a `@kind:test` block
becomes `<name>.test.ts`. Block names may contain `/` to create subdirectories.
Every artifact is prefixed with an auto-generated banner (`Auto-generated by
SpecLang … DO NOT EDIT`).

**Placement matters for tests.** The cascade runs `npx vitest run` on generated
test files; vitest only collects what is inside its `include` (`tests/**/*.test.ts`,
see `vitest.config.ts`). So:

- seed under `tests/…` → generated tests actually execute (`Tests: 1/1 passed`)
- seed anywhere else → the tests are written but **never collected**, and the
  cascade still prints `Converged: Yes` on a `0/0` run

That second case is a vacuous pass. The driver treats it as a failure (§7).

All output locations above are gitignored (`generated/`, `.speclang/`), so a
loop leaves the working tree clean.

## 3. The one-command loop

`scripts/agent-driver/drive.mjs` is the hardened entry point. It runs the
stages, checks the result, and writes the progress record. It ships with this
repository (a checkout of SpecLang, not the published npm package — `package.json`'s
`files` list does not include `scripts/`).

```
node scripts/agent-driver/drive.mjs --seed <path> [options]

  --seed <path>      single-seed spec file (required)
  --run-dir <path>   where progress.{json,jsonl,md} land (default: the seed's dir)
  --skip-validate    skip the validate stage
  --no-recheck       skip the determinism re-run
  --json             print the progress record as JSON
  --quiet            suppress the per-stage lines
```

Stages and what each one proves:

| Stage | Command it runs | Proves |
|---|---|---|
| `preflight` | `node --version`, `test -f dist/src/cascade/index.js` | the CLI is built and the seed exists |
| `validate` | `bin/speclang validate <seed>` | the seed parses (header + blocks) |
| `cascade` | `bin/speclang cascade -v <seed>` | the seed generated something, and how many tests ran |
| `verify` | internal | every reported artifact exists, is non-empty, and has a body beyond the banner; test blocks actually executed |
| `recheck` | `bin/speclang cascade <seed>` (second run) | the artifact set is byte-identical across runs |

Exit codes: `0` loop complete · `1` loop ran but the result is unacceptable
(reason recorded) · `2` the driver could not run (bad args, missing seed,
missing `dist/`).

The progress record — written even on failure, so a failed loop is diagnosable:

| File | Shape |
|---|---|
| `progress.json` | full record: schema, seed, generated dir, timestamps, `ok`, `reason`, `stages[]`, `artifacts[]` (path, bytes, body_bytes, sha256), `warnings[]` |
| `progress.jsonl` | one JSON line per completed run (append-only history) |
| `progress.md` | the same record as a Markdown table — paste it into the task log |

## 4. Runbook (fresh clone, verbatim)

Every command below was run from the repository root of a fresh checkout on
2026-11-17 and exited 0.

```bash
npm ci
npm run build
```

`npm ci` installs from `package-lock.json` and runs the two postinstall helpers.
`npm run build` is `tsc`; the cascade's runtime lives in `dist/`, and the driver
refuses to start without it.

```bash
./bin/speclang --version
./bin/speclang status
```

`--version` prints `1.0.0`. `status` prints the project path, daemon state and
the spec count (`Specs: 452 (450 .spec.md + 2 .scl)` on this checkout) — the
cheap "is this tree the one I think it is" probe.

```bash
./bin/speclang validate scripts/agent-driver/seed.example.spec.md
```

Validates only the seed: `✓ Passed`, `Validation Summary: 1 files`.

```bash
./bin/speclang cascade -v scripts/agent-driver/seed.example.spec.md
```

Generates `scripts/generated/greeting.ts` and `scripts/generated/farewell.ts`
and prints:

```
✅ Cascade complete
   Generated: 2 files
   Converged: Yes
   - /…/scripts/generated/greeting.ts
   - /…/scripts/generated/farewell.ts
```

`-v` adds the per-block trace and the `[Cascade] Tests: x/y passed` line. Keep
`-v` on: it is the only place the test counts appear.

```bash
node scripts/agent-driver/drive.mjs --seed scripts/agent-driver/seed.example.spec.md --run-dir .speclang/agent-driver
```

The whole loop in one command. Expected tail:

```
## SpecLang agent-driver run — PASS
| preflight | … | 0 | …
| validate  | … | 0 | …
| cascade   | … | 0 | …
| verify    | … | 0 | …
| recheck   | … | 0 | …
| `scripts/generated/greeting.ts` | 442 | 261 | 4f2cec8a1506 |
| `scripts/generated/farewell.ts` | 300 | 119 | 239fdd018c12 |
```

```bash
node scripts/agent-driver/drive.mjs --seed scripts/agent-driver/seed.example.spec.md --run-dir .speclang/agent-driver --json
```

Same run, machine-readable on stdout — with `--json` the whole stream is one
JSON document, so `... --json | jq .ok` works.

```bash
./bin/speclangd status
```

`🔴 Daemon: Stopped` (or the live PID). Read-only: it inspects the pid/state
files and never starts a daemon.

### What the driver should report back

1. the seed path and the resolved artifact directory,
2. `ok` plus every stage's exit code (from `progress.json`),
3. the artifact table with byte sizes — a count is not evidence, sizes are,
4. any `warnings[]`, especially blocks that produced no artifact.

## 5. Writing the seed (the part that decides the loop's outcome)

The driver's only creative act is the seed. Rules that follow from how the
parser and generator actually behave (`src/cascade/index.ts`):

1. **Header first.** `# speclang-header lines:N` declares how many lines the
   header occupies, *including* the declaration line and the closing `---`.
   A 6-line header (declaration + `id`, `version`, `layer`, `target_lang` + `---`)
   is `lines:6`. A wrong count makes `validate` parse the body as YAML and fail.
2. **One `### @block::<name> @kind:<kind>` per artifact**, each followed by a
   language-tagged fence (`ts`, `typescript`, or `speclang`). An untagged fence
   is ignored; a block with no fence is skipped (a warning, not an error).
3. **What the body says is what lands on disk** — the cascade does not summarise
   or repair it. Keep each block a complete, self-contained module.
4. **`@kind` decides whether a file appears.** `code` and `test` (with a fence)
   produce files; other kinds (`endpoint`, `operation`, `doc`, …) are descriptive
   and are skipped. The driver lists every skipped block under `warnings[]`.
5. **Test blocks go where vitest can see them** (§2). Otherwise the loop reports
   a vacuous convergence and the driver stops you.
6. **`id` must start with `@`** (`id: "@agent-driver/baseline"`); the validator's
   id rule enforces it.

A minimal seed that satisfies all six is
[`scripts/agent-driver/seed.example.spec.md`](../scripts/agent-driver/seed.example.spec.md).

## 7. What the driver refuses (negative probes)

Each probe below was run and failed exactly as stated. They are **expected to
exit non-zero** — that is the point of the driver.

| Probe | Observed result |
|---|---|
| Seed whose blocks are all `@kind:endpoint` / unfenced | `speclang cascade` exits **0** with `Generated: 0 files`, `Converged: Yes` and a warning; the driver exits **1**: `cascade reported no artifacts (exit 0 with zero files is a no-op, not a pass)` |
| Seed with a `@kind:code` block whose code fence is empty | the cascade writes a **181-byte banner-only** artifact; the driver exits **1**: `artifact carries only the generated banner, no body` |
| Seed with a `@kind:test` block placed outside `tests/**` | cascade prints `[Cascade] Tests: 0/0 passed`, `Converged: Yes`; the driver exits **1**: `test block(s) were generated but 0 tests executed — "converged" is vacuous; place the seed so <seed-dir>/../generated lands inside vitest's include (tests/**)` |
| Second cascade run produces different bytes | the driver exits **1**: `cascade is not reproducible: …` |
| `--provider deepseek` | SpecLang itself exits **1**: `Unsupported LLM provider "deepseek". Expected openai, openrouter, anthropic, or google.` |
| Missing seed / unknown flag | the driver exits **2** before doing anything |

The first three are the reason this script exists: `speclang cascade`'s exit code
alone cannot distinguish "generated two files" from "generated nothing".

## 8. Optional: the LLM expansion path (Path B)

Use this only when the task needs a model to write content. It is the mechanism
behind "speclang fills in the extra prompts": one seed trigger, many artifacts.

**Dry run — no key, no network, exit 0.** The driver can (and should) prove the
request mapping before spending tokens:

```bash
./bin/speclang agent --trigger scripts/agent-driver/seed.example.spec.md --provider openai --dry-run --json
```

```json
{
  "agent": "speclang-spec-writer",
  "provider": "openai",
  "model": "gpt-5-mini",
  "thinking": "medium",
  "providerParams": { "reasoning_effort": "medium" },
  "content": "",
  "dryRun": true
}
```

The agent is chosen from the trigger: `*.spec.md` → `speclang-spec-writer`,
`src/…` → `speclang-code-gen`, `tests/…` → `speclang-test-writer`, anything else
→ `speclang-coordinator`.

**Live.** Same command without `--dry-run`, with a provider key in the
environment; `--model`, `--base-url`, `--thinking <none|low|medium|high>` and
`--api-key` override the defaults. `speclang agent` prints the model's answer on
stdout — it writes no files itself.

**Wiring it to disk.** The daemon consumes routed tasks and drives the
coordinator, which persists whatever the model marked:

```bash
./bin/speclangd start -d      # detached; pid in .speclang/speclangd.pid
./bin/speclangd status
./bin/speclangd stop
```

`status` reports `🟢 Daemon: Running` with PID/uptime once started and
`🔴 Daemon: Stopped` after `stop`; the watcher covers `specs/`, `tests/` and
`generated/`, and its transcript is `.speclang/speclangd.log`. All three
commands exit 0 and are read-only apart from the pid/state files.

- A model answer containing `# generated/<path>` (also `## FILE: …`, `FILE: …`)
  section markers is split and written to those paths; with no marker the whole
  answer goes to the routed task's single target (`CascadeCoordinator.persistAgentOutput`).
- Writes are confined to the project root; anything outside is refused.
- Per-invocation history — agent, timestamp, success/failure, files touched,
  cascade depth — is persisted to `.speclang/cascade_state.json`.
- Budgets: `SPECLANG_AGENT_TIMEOUT_MS` (default 900000 = 15 min) bounds one
  session, and the coordinator's verification gates (references, `tsc --noEmit`,
  `pytest`) run per wave.
- Provider selection, model defaults and base URLs: `docs/CONFIGURATION.md`
  (`SPECLANG_PROVIDER`, `SPECLANG_MODEL`, `SPECLANG_BASE_URL`, `SPECLANG_BIN`).

What this path does **not** give you: a provider outside the four above, a
guarantee that the model hit the file names you asked for (check the
`progress`/`cascade_state.json` artifacts), or determinism. When the driver needs
evidence rather than invention, use Path A.
